圣农经营智能中枢

把分散的经营事实，持续转化为可追溯的经营行动。

门店、仓储、渠道里的每一次业务变化，都可能藏着值得查一查的问题。这套机制把异常信号变成一个个独立的调查案件：Agent 负责查清事实，管理层负责做决定，执行完还要用真实结果回头验证。每个案件从信号到结案全程留痕，随时可以回头复查。

01 · 为什么需要

系统记住了事实，却没有人接住问题

圣农的零售生意横跨多区域、多渠道，数据散在不同的系统里。企业缺的往往不是更多报表，而是一套机制：把散落的事实，持续变成有人查、有人拍板、有人验证的经营行动。

业务事实变化 → 发现值得调查的问题 → 查清证据 → 管理层拍板、组织执行 → 用真实经营结果验证 → 沉淀成下一次的能力。

我们不重做 ERP，也不追求一步到位的大平台，而是先从价格这件具体的事做起，跑通一个小而完整、能审计、能验证的闭环。

事实状态当前结论
公开资料支持圣农经营多区域、多渠道，数据分散；年报还提出产销协同、精益仓储、全渠道等方向（官方赛题、2025 年年报）。
方案设计推断用语义层、经营事件、领域调查方法、全程留痕和人工治理组成闭环，值得先在价格域小规模验证。
待企业验证真实痛点、系统字段与接口、组织分工、历史案例、价值基线和目标租户能力，都要到圣农现场才能定。

02.1 · 正式关闭案件

只有正式关闭的完整案件才能进入

只有按"成功解决、合法例外、系统误报"三类之一正式关闭、记录完整的案件，才能进入能力进化；任务完成、暂不处理、风险接受、信息不足都不算。

输入
01 正式关闭的完整案件与全部留痕。
产物

边界
不设低成本初筛；不完整、未关闭的案件一律不进入。

LOOP 01 · 经营事件循环

事实 → 经营结果

业务数据一有异常迹象，系统就生成一条候选信号；确认是值得调查的经营事件后，自动建立一个独立案件，并给 Agent 一份入场事实清单（经营事件包 v1）。Agent 按领域方法一步步查证，管理层看完证据做决定，执行之后再用真实经营结果回头验证。

01 → 02案件按"成功解决、合法例外、系统误报"之一正式结案，留下完整记录。任务点完"完成"不算数；暂不处理、接受风险、信息不足，都不能提前进 02。
02 → 01改进先由人核实，再在隔离环境验证，管理层批准后才回到 01 真实业务里小范围运行。一次成功不会自动改写生产配置；验证失败必须回滚并返回诊断。
01、02 → 03价格试点跑出能核验的结果，才有坐下来谈扩域的资格。不自动触发扩域，也不代表企业已经认可候选场景。
03 → 01企业采纳的新场景，作为独立业务域的小试点，重新走一遍 01。不把价格案件直接换成别的域；新事件仍建立自己的案件和 Agent 上下文。
04 · 共同能力底座

不是第四个循环，而是三个循环共同的底座

四组底层能力被三个循环共用，在使用中不断校正，并复用到更多业务域。

能力组在方案中的作用必须保持的边界
权威事实与语义SAP、POS、WMS、CRM、飞书仍是事实的唯一来源；语义层负责把各系统的字段翻译成统一的经营语言。KWeaver 是候选的通用底座，但它不自带圣农的经营规则，更不会取代 ERP。
Agent 调查与工具Agent 按事件类型加载对应的领域方法（Skill），用受控工具一步步查证。Agent 不绕过权限直连业务系统，不替管理层做决定，也不会在运行中自己改自己。
事件、证据与版本从信号到结案，每一步的来源、时间、版本、权限全部留痕，可回放、可纠错。证据库是权威记录；飞书页面只是协作投影，不是第二套账。
协作与治理谁该知道、谁补证、谁决策、谁执行、谁批准能力变更，都有明确规则，必要时人随时接管。高影响的经营动作和能力变更必须由有权的人批准；目标租户能力没验证前，一律按未知处理。

06 · 事实边界

这些不是缺陷，而是方案的可信度来源

当前是方案设计与离线原型阶段。以下内容一律待企业验证，本网站不作任何生产事实宣称。

  • 圣农真实系统的字段、接口和数据质量，要等企业给的字段字典和脱敏样本到了才能核。
  • 圣农真正的经营规则、合法例外和审批权限，要和业务负责人逐条对过才算数。
  • Aily 和飞书在目标租户里到底能用到什么程度，要做一次最小权限的端到端实测。
  • 证据库的落库、事务和回放机制，先用 24.9 元这个模拟案件完整跑一遍。
  • 03 的候选场景合不合圣农的实际节奏，要看试点结果，和管理层一起定。
